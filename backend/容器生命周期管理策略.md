这是一个关于**容器生命周期管理**的核心问题。在实训平台（特别是涉及 GPU 资源）的场景下，做出的选择直接影响服务器的负载能力和维护成本。

基于你提供的数据库表结构，特别是 `Container` 表和 `UserLab` 表的分离设计，我的建议是：**采用“即用即弃”策略（Stop & Remove）**。

也就是说：**当用户结束实验时，应该直接停止并删除容器，同时删除数据库中的 `Container` 记录。**

### 为什么选择“删除”而不是“停止”？

1. **资源释放（最重要）**：
* **GPU/内存**：`docker stop` 虽然释放了 CPU，但某些配置下可能不会完全释放显存或系统资源句柄。
* **端口占用**：你的 `Container` 表记录了 `host_port`。如果容器只是 Stop 而不删，这个端口就被“占着茅坑不拉屎”。如果几百个学生都 Stop 了，你的服务器端口可能就被耗尽了，新来的学生无法启动。


2. **数据持久化已解决**：
* 我们在之前的代码中已经实现了挂载卷：`/data/workspace/u{uid}/e{eid}`。
* **核心逻辑**：只要学生把代码和文件保存在 `/workspace` 下，容器被删除了，文件依然在宿主机硬盘里。下次启动新容器挂载同一个目录，感觉就像“断点续传”一样。


3. **环境一致性**：
* 如果只 Stop，学生如果把环境搞乱了（比如误删了系统文件），下次 Start 还是那个烂摊子。
* 如果 Delete，下次由镜像重新 Run，学生得到的是一个全新的、干净的系统环境（除了 `/workspace` 数据），容错率更高。

### 具体的实现方案

我们需要完善 `DockerService` 和 `ContainerService`，实现**停止并清理**的逻辑。

#### 1. 修改 `backend/app/services/docker_service.py`

增加停止和删除容器的方法。

```python
# ... 之前的代码 ...

class DockerService:
    # ... run_container 等代码 ...

    @staticmethod
    def stop_remove_container(container_id: str):
        """
        停止并删除容器
        """
        try:
            # 获取容器对象
            container = DockerService.client.containers.get(container_id)
            
            # 停止容器 (如果正在运行)
            # timeout=1 表示给1秒时间让进程自己退出，然后强制kill，加快速度
            container.stop(timeout=1) 
            
            # 删除容器 (remove 也会清理掉匿名卷，但不会删掉我们要的 bind mount)
            container.remove()
            
            print(f"容器 {container_id} 已清理")
            return True
        except docker.errors.NotFound:
            print(f"容器 {container_id} 已经在Docker中不存在了")
            return False # 容器本来就不在，也算成功
        except Exception as e:
            print(f"停止容器失败: {e}")
            raise e

```

#### 2. 修改 `backend/app/services/container_service.py`

增加业务层的停止逻辑：不仅要调 Docker，还要删数据库。

```python
from sqlmodel import Session, select
from fastapi import HTTPException
from app.models.lab import Container
from app.services.docker_service import DockerService

class ContainerService:
    # ... 之前的 get_or_create_container 代码 ...

    @staticmethod
    def stop_experiment(session: Session, user_id: int, exp_id: int):
        """
        停止实验：清理Docker资源 + 删除数据库记录
        """
        # 1. 查数据库找容器记录
        statement = select(Container).where(
            Container.user_id == user_id,
            Container.experiment_id == exp_id
        )
        container_record = session.exec(statement).first()

        if not container_record:
            # 只有记录不存在，说明本来就没在跑，直接返回成功
            return {"message": "实验未运行"}

        # 2. 调用 DockerService 清理物理容器
        # 即使数据库有记录，Docker里可能已经被意外删了，所以这里要做容错
        try:
            DockerService.stop_remove_container(container_record.container_id)
        except Exception as e:
            # 记录日志但不要崩溃，继续清理数据库，否则产生死数据
            print(f"警告: Docker清理异常，但这可能不影响数据库清理. {e}")

        # 3. 删除数据库中的 Container 记录
        # 注意：这里我们只删 Container 表，UserLab 表的状态保留或更新，不删 UserLab
        session.delete(container_record)
        session.commit()

        return {"message": "实验已停止，资源已释放"}

```

#### 3. 新增 API 接口 `backend/app/api/v1/endpoints/containers.py`

### 进阶：如何防止“学生忘了点停止”？ (僵尸容器治理)

这是实训平台最大的痛点。学生做完作业直接关浏览器，容器会在后台一直跑，空耗服务器资源。

建议引入 **“心跳机制”** 或 **“定时清理策略”**。由于现在还没引入 Redis 或 Celery，我们可以用一个简单的 **FastAPI 启动时挂载的定时任务 (APScheduler)** 或者 **惰性清理**。

**最简单的策略（Lazy Cleanup）：**

在 `get_or_create_container` (启动实验) 的时候，顺便检查一下该用户有没有其他**过期**的容器。

但更推荐的策略是 **“定时巡检”**。这里给出一个简单的巡检脚本思路，你可以放在 `backend/app/core/scheduler.py` (假设文件) 中：

```python
# 这是一个概念代码，需要安装 apscheduler
# pip install apscheduler

from apscheduler.schedulers.background import BackgroundScheduler
from sqlmodel import Session, select
from datetime import datetime, timedelta
from app.db.session import engine
from app.models.lab import Container
from app.services.docker_service import DockerService

def cleanup_expired_containers():
    """
    清理运行超过 24小时 的容器 (或者根据业务需求定)
    """
    with Session(engine) as session:
        # 找到所有运行时间过长的容器
        expiration_time = datetime.utcnow() - timedelta(hours=24)
        statement = select(Container).where(Container.created_at < expiration_time)
        expired_containers = session.exec(statement).all()

        for container in expired_containers:
            print(f"自动清理过期容器: {container.container_id} (User: {container.user_id})")
            # 1. 删 Docker
            try:
                DockerService.stop_remove_container(container.container_id)
            except:
                pass 
            # 2. 删库
            session.delete(container)
        
        session.commit()

def start_scheduler():
    scheduler = BackgroundScheduler()
    # 每小时检查一次
    scheduler.add_job(cleanup_expired_containers, 'interval', hours=1)
    scheduler.start()

```

然后在 `main.py` 的 `lifespan` 里调用 `start_scheduler()`。

### 总结数据库表状态流转

基于你的 `UserLab` (记录学情) 和 `Container` (记录资源) 分离的设计，状态流转非常清晰：

1. **初始状态**：
* `UserLab`: status="unstarted" (未开始)
* `Container`: (无记录)


2. **点击“开始实训”**：
* `UserLab`: status="running" (后端更新)
* `Container`: **插入一条记录** (container_id=xxx, port=8888)


3. **做实验中**：
* 前端每隔几分钟发送心跳（可选），或者后端定时检查。


4. **点击“停止实训”** (或超时自动清理)：
* `UserLab`: status="stopped" (或保持 running，看你业务定义。通常建议由 unstarted -> running -> submitted)
* `Container`: **删除记录** (资源彻底释放)


5. **点击“提交报告”**：
* `UserLab`: status="submitted"
* `Submission`: 插入一条记录



这样的逻辑既保证了资源的有效利用，又保证了学生数据的安全（都在宿主机硬盘里）。
